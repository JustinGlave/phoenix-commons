````markdown
# Known Issues

A short list of caveats that are real, reproducible, and **not fixable
in the Command Center / Phoenix Tool wizard source code**. They live
here so anyone consuming a freshly generated Phoenix tool knows where
to look first when a frozen-exe step misbehaves on the current
developer laptop.

## 1. Corporate AV (SentinelOne / S1) quarantines PyInstaller bootloaders

### What happens

When `build.bat` runs in a generated Phoenix tool on the current
developer laptop:

- PyInstaller builds `dist\<ExeStem>\<ExeStem>.exe` and
  `dist\<ExeStem>\_internal\` cleanly.
- Inno Setup compresses the freshly built exe into
  `dist\<ExeStem>Setup.exe` successfully (the bootloader is on disk
  for ~30 seconds while Inno reads it).
- Within seconds after `build.bat` returns, the corporate endpoint
  protection (SentinelOne / "S1"-class agent) deletes
  `<ExeStem>.exe` from disk based on a content heuristic on the
  PyInstaller bootloader binary.
- `_internal/` (Qt DLLs, Python runtime, etc.) is left intact —
  only the bootloader exe is hit.
- The auto-updater zip generated by `build.bat`'s `Compress-Archive`
  step similarly excludes the now-missing exe.

### What this means

- **Source-mode dogfood works fully.** A fresh standalone scaffold
  generated through the wizard installs cleanly into a Python 3.14
  venv, passes `compileall`, passes `pytest` (smoke tests + the new
  release-zip validator tests), and opens its themed
  `MainWindow` offscreen. See
  `phoenix-commons/docs/rollout/phase-6-standalone-dogfood-report.md`
  for the verbatim evidence chain.
- **Frozen-exe runtime cannot be verified on this laptop.** The
  bootloader is gone before any launch attempt. No `Setup.exe`
  install has been performed end-to-end. No `%LOCALAPPDATA%\ATS Inc\…`
  install path has been validated.

### Is this a scaffold defect?

**No.** The exact same AV pattern has been documented across:

- Phase 4 (in-tree PyInstaller build of the phoenix-commons smoke app)
- Phase 4B-local (external-path build of the same smoke app — proved
  that build path doesn't matter; the signature is on the
  bootloader's contents)
- Phase 6 (the standalone dogfood through this very wizard)

None of those phases exercise different scaffold templates, yet the
behaviour is identical. The wizard, the templates, the scaffolds, the
release-zip validator (see `scripts/validate_release_zip.py` in any
generated Phoenix tool from Phase 6A onward) — none of them have
source defects that would cause this.

### What stays deferred until the AV gate clears

- **Commons-backed remains non-default in the wizard.** The Phoenix
  Tool — standalone radio is the default. The Phoenix Tool —
  commons-backed radio is enabled only when `commons_path` is
  configured, and its inline note still reads:
  > "ℹ Commons-backed template is available for source-mode testing.
  >  Frozen-exe runtime verification is still blocked by local AV."
- **Production tool retrofits (Phase 7) remain deferred.** Phoenix
  CAD, Phoenix Checkout, Job Tracker, and ValveMaster keep their
  current shipping installers and updaters until the AV gate clears.

### Resolution options

Any of these unblocks the frozen-exe gate. They are environmental
fixes — none of them require Command Center / Phoenix Tool source
changes:

1. **IT / S1 allow-list.** Ask whoever administers the corporate
   endpoint protection to allow-list the PyInstaller bootloader
   signature for the developer machine and/or for the
   `%LOCALAPPDATA%\ATS Inc\` install root. This is the lightest fix
   if IT is responsive.
2. **Code signing.** Obtain an Authenticode signing certificate and
   sign the PyInstaller-produced exe inside `build.bat` (after the
   PyInstaller step, before Inno Setup). Signed bootloaders generally
   bypass content-heuristic AV signatures because the publisher
   identity is checked first.
3. **Approved alternate build machine.** A build host without the
   same S1 signature in effect — e.g. a CI runner, a freshly imaged
   workstation with a narrower AV profile, or a build-server VM —
   produces an unmodified exe that survives long enough to be
   packaged and shipped. End users on machines without the same
   signature would receive the resulting installer normally.

Any combination of the above is fine; option (2) is the most durable
long term but also the slowest to set up.

## Index

| Issue | Status | Resolution |
|-------|--------|------------|
| S1 / AV bootloader quarantine | Open (environmental) | IT allow-list, code signing, or alternate build machine |
````
